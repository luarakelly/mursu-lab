When I started this journal, I had a clear technical goal in mind: build a portfolio where I could share my projects. The idea was to have a space where I could show off my skill to future employers. But somewhere along the way, the project stopped being just about the portfolio.
It became something else entirely.

## The Shift: Why I Built It

As I began planning the portfolio, I realized I didn’t actually have a reliable way of structuring my own projects. Every idea I had eventually ran into the same problem: unclear stages, inconsistent execution, and too much time spent deciding _what is the next step_ instead of building.
So I stepped back and started designing a framework. Not for the portfolio itself, but for _how I build anything_.
That turned into a simple but structured workflow I now follow inside this journal/portfolio project. It defines how ideas move from concept → planning → implementation → reflection.
It sounds simple, but it changed how I approach building things.

## The Unexpected Output: A Personal UI System

While working on the journal and framework, I also started building a personal UI library.
At first, it was just a way to avoid repeating UI patterns. But it quickly became more than that: a small design system focused on **composition, primitives, and semantic structure** rather than heavy component abstraction.
This introduced me to a deeper understanding of **headless UI design** and how systems can be built from layers instead of monolithic components.
The goal is not just reuse. It’s to create a foundation I can carry into future projects so I can move faster without rebuilding the same UI logic every time.

## The Over-Engineering Problem

A big theme throughout this process has been finding the balance between structure and over-engineering.
At the beginning, I leaned heavily into planning everything upfront. Every component, every layer, every abstraction had to “make sense” in a system.
But at some point, that level of structure starts slowing things down instead of helping.

I had to actively adjust my approach:

-- Keep the system flexible
-- Avoid unnecessary abstraction
-- Build only what solves a real problem _right now_

This tension between planning and execution is still something I’m refining as I go.

## What Comes Next

This experience has naturally evolved into multiple themes that I want to explore further in this journal:

1. Expanding the UI library from the journal project and turn into a reusable systui library
2. Refining the project framework through actual use
3. Exploring over-engineering vs clarity in system design

This first entry feels less like a project update and more like the start of a process.

Which is probably exactly what it is.
